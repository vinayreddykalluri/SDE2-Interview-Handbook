## Here is what's inside. Judge it in thirty seconds.

Sort a three-element list. Get the same list back, in the wrong order:

```java
Comparator<Integer> fuzzy = (a, b) ->
        Math.abs(a - b) <= 10 ? 0 : Integer.compare(a, b);   // "within 10 is a tie"

List<Integer> scores = new ArrayList<>(List.of(15, 5, 0));
scores.sort(fuzzy);
System.out.println(scores);      // [15, 5, 0]  - nothing moved
```

Most Java material tells you a comparator must be transitive. This one shows you the
sort that quietly lies, measures how often it happens — **10,454 of 20,000 random
lists came out misordered** — and then admits something uncomfortable:

> When I first checked this, I compared *adjacent* pairs of the output, found zero
> violations, and would have cleared the comparator. The defect only shows across
> non-adjacent pairs. That mistake is in the chapter, because it is the mistake you
> would make too.

That is the standard the whole library is written to. Every number is computed before
it is printed. Where I got something wrong in a draft, the correction is in the text
rather than quietly deleted.

## Why this exists

I have sat on both sides of the SDE-2 loop, and the same thing happens every time.
A candidate can use `HashMap` daily for four years and still not be able to say what
happens when a key mutates after insertion. Not because they are careless — because
almost everything written about collections is a restatement of the Javadoc.

So the rule here is: **if a chapter makes a claim, it has to show it.** A `HashMap`
entry that is present in `size()` and in iteration but unreachable by key. Two
`BigDecimal`s into a `TreeSet` and one comes out. A loop that is linear over
`ArrayList` and quadratic over `LinkedList` — 24,995,000 link hops against 10,000.

And the discipline that took the longest to get right: separating what the
**specification guarantees** from what **OpenJDK happens to do**. Confidently
over-specific answers are the classic senior-level failure, and every chapter labels
the difference explicitly.

## Run it locally

```bash
make bootstrap     # macOS only; sets up the toolchain
make install       # venv + authoring dependencies
make doctor        # environment preflight
make serve-web     # the full portal with the handbook mounted at /docs/
```

Then open <http://127.0.0.1:8000/>. Use `make serve` if you only want the MkDocs
handbook. Everything routes through `make` — see the
[local-development guide](docs/project/local-development.md) for prerequisites and
troubleshooting.

**Markdown is the single source of truth.** The website, the 43 PDFs, and the DOCX
are all generated from it. Never hand-edit anything under `dist/` or `site/`.

## Quality gate

```bash
make validate      # layout, navigation, links, Java, portal metadata, assets
make validate-all  # the strict path CI uses, including PDF integrity
make build-site
```

The suite checks repository layout, MkDocs navigation, internal links, Java
compilation and smoke execution, portal metadata, local assets, JavaScript syntax,
and — unusually — the PDFs themselves: page counts against declared bands, manifest
agreement, blank pages, and pages with no extractable text. Every validator here has
been fault-injected to prove it actually fails on bad input.

Published-book changes also run:

```bash
cd books/java-sde2-interview-preparation-series
python3 scripts/validate_book.py --source-only
python3 scripts/validate_series.py --source-only
```

## Contributing

The most valuable contribution is not a new chapter — it is **finding a place where
the book is wrong, or where an explanation did not land.** Both are real bugs here.

Good first contributions:

- an accuracy correction, with the reproduction
- a paragraph that confused you, rewritten so it wouldn't have
- a compiling edge-case example that breaks a claim
- a diagram for something currently explained only in prose
- a PDF layout defect, with the page number

Start with the [contribution guide](.github/CONTRIBUTING.md) and use the issue form
that matches the change. Keep prose and runnable code in sync. Accepted original work
is credited to you in the [authorship record](docs/community/authors.md), the Git
history, and the pull request.

The public backlog is coordinated in
[issue #27](https://github.com/vinayreddykalluri/SDE2-Interview-Handbook/issues/27).
All 41 books are publication editions, so contributions now deepen an existing volume
rather than adding a parallel roadmap. Large expansions should start with an issue.

Conduct and stewardship: [Code of Conduct](.github/CODE_OF_CONDUCT.md) ·
[Governance](docs/community/governance.md) · [Security](.github/SECURITY.md) ·
[Support](.github/SUPPORT.md)
