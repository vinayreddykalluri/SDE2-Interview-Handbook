# Contributing

Thank you for helping make Java and SDE-2 interview preparation clearer, more accurate, and more accessible. Contributions of every size are welcome.

## Good first contributions

- Report one confusing paragraph and explain where your understanding broke.
- Add an edge case to an existing executable example.
- Correct a Java-version, numeric-promotion, collection, or complexity claim.
- Improve alt text, diagram labels, navigation, or PDF readability.
- Add a predict-the-output or debugging exercise with a reasoning-based solution.
- Verify a chapter against a primary source and record the source boundary.

Look for GitHub issues labeled `good first issue`, `content`, `accuracy`, `exercise`, `diagram`, or `build`.

## Before a large change

Open a proposal issue before:

- adding or removing a chapter or volume;
- changing the recommended learning path;
- introducing a new build dependency;
- changing the Java baseline;
- rewriting a substantial section;
- changing licensing, governance, credits, or cover identity; or
- duplicating material from another focused volume.

This prevents good work from landing in the wrong book.

## Editorial standard

Important topics should normally include:

1. beginner intuition;
2. why the concept matters;
3. exact Java syntax or API behavior;
4. a compiling example with expected output;
5. a dry run, state table, or diagram where useful;
6. realistic edge cases and common failures;
7. an interview explanation and follow-up; and
8. focused practice with a separated reasoning solution.

Do not add length without adding learning value. Prefer one smaller prerequisite example before a sophisticated example. Keep implementation-specific behavior labeled and avoid unsupported universal performance claims.

## Accuracy rules

- Target Java 21 unless the section labels another version.
- Prefer the Java Language Specification, JVM Specification, Java SE API, OpenJDK JEPs, and official project documentation.
- State whether a claim is guaranteed, typical, expected, amortized, version-specific, or workload-dependent.
- Widen before arithmetic that can overflow.
- Never describe Java as pass-by-reference.
- Do not use `==` as object value comparison.
- Do not claim HashMap operations are unconditionally guaranteed `O(1)`.
- Do not assume PriorityQueue iteration is sorted.
- Keep invalid code outside normal compilation and label the intended failure.
- Use `Integer.compare` or another safe comparator rather than subtraction.

## Repository workflow

1. Fork the repository.
2. Create a focused branch from the default branch.
3. Change the smallest coherent set of files.
4. Add or update examples, exercises, solutions, and reports when the change requires them.
5. Run relevant checks.
6. Inspect the generated PDF pages affected by your change.
7. Complete the pull-request template, including authorship and licensing declarations.

Keep unrelated formatting changes out of the same pull request.

## Build commands

Set up Python dependencies:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

Build one focused volume:

```bash
python3 scripts/build_series.py --volume 05 --skip-index
```

Build the complete focused series:

```bash
python3 scripts/build_series.py
```

Build the master edition:

```bash
python3 scripts/generate_diagrams.py
python3 scripts/build_book.py
```

## Validation

At minimum, validate changed Markdown and standalone Java. For release-affecting work, rebuild and inspect the PDF.

```bash
python3 scripts/validate_book.py --source-only
python3 scripts/validate_series.py --source-only
```

Compile a focused companion when present:

```bash
javac --release 21 -Xlint:all -Werror PathToCompanion.java
java CompanionClassName
```

For PDF changes:

- confirm page count and metadata;
- inspect the cover, contents, affected chapter openers, changed diagrams/tables/code, author/credit page, and publishing notes;
- check clipped or overlapping content;
- check near-empty unexpected pages; and
- update the build report or validation evidence.

## Diagrams

Prefer reproducible diagrams generated by a script when exact indexes, arrows, bit positions, or state labels matter. Match the existing navy/teal/gold palette and provide descriptive Markdown alt text. Do not submit an image that contains third-party copyrighted material without compatible permission and attribution.

## Authorship and contributor credit

The project credits people, not tools.

- State which prose, code, exercises, solutions, diagrams, or reviews are your original work.
- Add or update [AUTHORS.md](AUTHORS.md) for publication-level contributions.
- Keep your Git author name/email configured as you want it recorded publicly.
- If the work has multiple authors, use Git co-author trailers where appropriate.
- Disclose meaningful AI assistance in the pull request. You remain responsible for checking every claim and line.
- Never submit confidential employer material, private interview questions, leaked assessment content, or material copied without permission.

The Editor-in-Chief confirms publication scope and credit. The Chief Auditor confirms accuracy, originality, and validation evidence.

## Review process

Reviewers may request changes for prerequisite order, beginner clarity, Java accuracy, scope, tests, attribution, or PDF usability. A correct advanced explanation may still need a simpler lead-in. A beautiful diagram may still need a proof or accessible text alternative.

The Editor-in-Chief makes final editorial decisions. The Chief Auditor may block release for unresolved technical, licensing, attribution, or validation defects. See [GOVERNANCE.md](GOVERNANCE.md).

## Community expectations

Be specific, patient, and evidence-based. Critique the material, not the contributor. Follow [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).
